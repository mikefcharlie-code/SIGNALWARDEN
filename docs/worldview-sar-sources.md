# Where the SAR imagery comes from

## Chosen source: ASF's public Sentinel-1 archive

The [ASF Search API](https://www.earthdata.nasa.gov/data/tools/asf-searchapi) is a publicly available NASA Earthdata catalog interface. Its [keyword reference](https://docs.asf.alaska.edu/api/keywords/) documents platform/product filters, geographic rectangles, acquisition dates, GeoJSON output, and result limits. SignalWarden AI requests Sentinel-1 **GRD_HD** products, with no authentication and a maximum of 50 records. Results are sorted newest-first within the returned set. If the limit is reached, the UI warns that completeness and the absolute newest acquisition are not guaranteed; users must narrow the query. The tested API rejected `sort=-startTime`, so no unsupported server-sort parameter is used.

A real, unauthenticated search for `bbox=-78,38,-76,40`, acquired September 23 through October 23, 2026, returned 14 GeoJSON features. The newest returned file ID was `S1D_IW_GRDH_1SDV_20261021T230634_20261021T230659_005120_009B33_6409-GRD_HD`, acquired October 21, 2026, 23:06:34–23:06:59 UTC. These are provider-returned values, not invented freshness or imagery. Its platform is Sentinel-1D, sensor C-SAR, mode IW, polarization VV+VH, absolute orbit 5120, relative path 4, ascending. The catalog's `processingDate` equals its acquisition start; the UI labels the field explicitly as ASF processingDate and does not reinterpret or correct it. Publication time, pixel spacing, and numeric spatial resolution were not supplied and remain unknown.

The catalog returned HTTP 200 with `Access-Control-Allow-Origin` matching the supplied browser Origin. An actual production-build browser search also succeeded. Requests without an Origin header did not demonstrate CORS behavior; those earlier observations were not treated as proof of browser support.

## Genuine imagery, not just catalog metadata

The selected feature's public browse URL points to ASF's `datapool` host. It redirects through `sentinel1.asf.alaska.edu`, then a provider-issued short-lived CloudFront delivery URL. Following that validated chain anonymously returned HTTP 200 `image/jpeg`: 642,370 bytes, 1024 × 755 pixels, for the product above. No Earthdata login or API key was used. A separate historical January 2025 California search and a returned JPEG were also verified.

These are ASF's reduced-resolution browse images. They are not georeferenced rasters or calibrated quantitative products. The panel displays the native browse image and a separate footprint-only SVG map. It does not pretend that the JPEG can be stretched into a registered map layer.

The strict browser downloader cannot safely follow the delivery chain directly: `redirect: error` rejects it, and the delivery endpoints did not establish browser-readable CORS for image bytes. Therefore the imagery workflow includes a **local, disabled-by-default, fixed ASF relay**, not an arbitrary proxy. It accepts only the selected Sentinel-1 product identifier, constructs the initial ASF path, and validates each redirect against the exact verified ASF origins, image filename, and CloudFront bucket path. Provider-signed delivery strings remain internal to the request; they are never stored, logged, embedded in code, or exposed to the browser. Delivery-host changes fail visibly.

The operator must explicitly start the Management API with `UCAS_PUBLIC_SAR_ENABLED=1`, expose only `/api/v1/public-imagery` on the UI's same origin, enable the SAR checkbox, and press **Load selected SAR preview**. Catalog search alone does not call the relay or download images. The source remains ASF throughout; redirect handling is not a fallback to another data provider.

## License and attribution

The [official Copernicus Sentinel legal notice](https://sentinels.copernicus.eu/documents/247904/690755/Sentinel_Data_Legal_Notice), linked by the [Copernicus Data Space terms](https://dataspace.copernicus.eu/terms-and-conditions), provides free, full and open access for lawful reproduction, distribution, public communication, adaptation, modification, and combination. It requires source notices and disclaims express/implied warranties. The specific notice and its conditions apply; other portal content is not automatically covered.

For these reduced-resolution provider browse images, the UI displays **“Contains modified Copernicus Sentinel data [acquisition year]; provider browse image and metadata retrieved from ASF DAAC.”** It does not claim NASA/ASF copyright ownership of underlying Sentinel data or provider endorsement. The [distributable notice](../apps/management-web/public/worldview-sar-notices.txt) keeps data terms separate from existing software licenses.

## Why not promise full-resolution access?

ASF's [download documentation](https://docs.asf.alaska.edu/asf_search/downloading/) distinguishes public discovery from authenticated product downloading with a free Earthdata Login account. This PR does not download full GRD ZIPs, ask for credentials, add tokens, run SAR processing, or claim calibrated scientific measurements.

Copernicus Data Space's open-data terms were reviewed as an alternative. Its data license does not imply that every processing or API workflow is anonymous. Planetary Computer's search listing flagged account-controlled Sentinel-1 RTC access, but that detail was not established from a fully rendered primary dataset page; it was not used as the basis for the implemented workflow. OPERA RTC appears in the [ASF dataset documentation](https://docs.asf.alaska.edu/datasets/using_ASF_data/), but this work did not verify a stable unauthenticated browser COG workflow and current coverage, so it is not offered as a hidden fallback.

Archive availability, new satellite identifiers, provider processing metadata, and latency can change. The UI exposes unsupported/missing assets and provider errors rather than inventing data or silently expanding connection permissions.

## Additional source: Umbra Open Data

The user's [HTTP bucket-browser URL](http://umbra-open-data-catalog.s3-website.us-west-2.amazonaws.com/) is a static website endpoint, not the application transport. The checked HTTPS website endpoint timed out, so no HTTPS support is claimed for that hostname. The **separate S3 REST endpoint**, `https://umbra-open-data-catalog.s3.us-west-2.amazonaws.com/`, was verified to return public catalog JSON, ListObjectsV2 XML, metadata JSON, and GeoTIFF byte ranges over HTTPS without AWS credentials. Replies expose `Access-Control-Allow-Origin: *` and support GET/HEAD. No downgrade to HTTP is implemented.

[Umbra's Open Data Program](https://umbra.space/open-data/) links the [AWS Open Data Registry entry](https://registry.opendata.aws/umbra-open-data/), which explicitly states **CC BY 4.0**, no AWS account required, and provides the public bucket ARN. A checked real STAC item (`stac/2025/2025-08/2025-08-03/3cc3baf2-7948-42e4-a9fa-f836ae553b8a/3cc3baf2-7948-42e4-a9fa-f836ae553b8a.json`) independently declares `properties.license: CC-BY-4.0` and Umbra Lab Inc as producer/processor/licensor/host. The registry's `https://umbra.space/open-license` link currently renders generic website Terms of Use, not the promised data-license text. This mismatch is disclosed; website restrictions are not silently substituted for, or represented as, the data's CC license. Vendor sidecar metadata does not itself establish a per-object license. The implementation labels the dataset-level registry basis, credits Umbra Lab Inc, links source objects and [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), and identifies local display transformations. CC BY requires appropriate credit, a license link, and indication of changes, without implying endorsement; the license deed also disclaims warranties and notes other rights may apply.

### Why bounded bucket browsing, not a fictional live search API?

The checked HTTPS STAC root `stac/catalog.json` has only 2025 and 2024 child links and an August 2025 Last-Modified timestamp. At least one reachable item has every `assets.*.href` empty. Those links cannot yield imagery, and constructing guessed replacements would violate provenance. The application instead lists **actual public object keys** from one S3 directory page per manual action, using `list-type=2`, `prefix`, `delimiter=/`, `max-keys=100`, and an explicit next-page token only when the operator presses Next. No recursive enumeration, automatic pagination, arbitrary-bucket requests, or background crawling occurs. Prefix/folder order is lexicographic, not acquisition recency; no complete-archive or global bbox/date search is claimed.

One verified genuine directory is `sar-data/tasks/Bingham Copper Mine/9c39dad2-3539-4a7a-b755-47278c11fc96/2024-08-28-18-05-33_UMBRA-08/`. Its actual `_METADATA.json` is 3,763 bytes. It supplies collect ID `404d4431-1653-4674-91c1-30eee63e9ac9`, acquisition start `2024-08-28T18:05:34Z`, end `2024-08-28T18:05:36.956238Z`, Umbra-08, X-band SAR, SPOTLIGHT, VV, descending track, right-looking, footprint and incidence angle, and GEC ground resolution 0.5 × 0.5 m. It does **not** supply a verified processing/publication time or pixel spacing, so those remain unknown. S3 object modification time remains an explicitly separate object-storage fact, never acquisition or publication time. STAC `created`/`updated` similarly are metadata lifecycle fields, not proof of first publication.

The matching actual `_GEC.tif` is **266,178,265 bytes**, and vendor metadata reports **16001 × 16001** full-resolution pixels. An explicit anonymous request for bytes 0–65535 returned **HTTP 206**, exactly 65,536 bytes, with byte-range support. The application does not silently download this large full file. Only an explicitly selected matching GeoTIFF can enter the bounded local overview decoder; no overview or unsupported data produces a visible failure, not a synthetic placeholder. Source-file resolution must not be confused with preview dimensions or pixel spacing. Original full-resolution object links are labeled as potentially large, separate manual downloads, not automatic preview reads.

Umbra and ASF sessions are independent. Switching the selector unmounts/cancels/clears the previous provider and requires a new opt-in. Umbra is not a relay destination for ASF and never becomes a fallback when another source fails. Both sources retain source identifiers, timestamps, licensing, failure/stale indicators, and SAR interpretation warnings.
